## Повторный запуск

Команды из папки проекта после создания и активации Python venv. Для API задайте DATABASE_URL отдельной локальной БД и тестовый SECRET_KEY по примеру конфигурации; не используйте рабочие подключения.

```bash
python -m venv .venv
# Активируйте .venv согласно ОС.
python -m pip install . -r requirements-dev.txt
python -m uvicorn app.main:app --host 127.0.0.1 --port 8000
```

Тесты в отдельном тестовом окружении:

В этой версии jobs нет Alembic-миграций. Таблицы новой БД создаются при старте
через `Base.metadata.create_all`; это добавляет отсутствующие таблицы, но не
меняет столбцы уже существующих таблиц.

22 октября исправлен доступ к чужим фоновым задачам. Владелец хранится в отдельной
новой таблице `task_ownerships`: её добавляет тот же `create_all` без изменения
существующих таблиц. Сначала обновляется и запускается API, затем worker/beat.
Записи без известного владельца остаются в БД, но скрыты от пользовательского API.
Проверяются фильтрация до пагинации, оба типа идентификаторов, все статусы,
владение до запуска worker, повторная обработка и сохранность старых записей.

Изолированный Docker-прогон 22 октября: 38 тестов на временной SQLite, fakeredis
и eager Celery; сеть контейнера отключена. Ruff, проверка форматирования и strict
mypy прошли. Эта повторная проверка не использовала PostgreSQL или отдельный
Celery worker; предыдущая проверка этого стека описана ниже.

```bash
python -m pytest -o addopts= -q
```

Docker-проверки использовали отдельную сеть, PostgreSQL *_test и Redis; реальные данные, платежи и внешние сообщения не затрагивались. Результат локального запуска не означает production-ready.
